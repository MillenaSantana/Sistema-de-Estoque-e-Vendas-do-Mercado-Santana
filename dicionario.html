Dicionário de Dados do Mercado Santana

1. Introdução

Este documento apresenta o dicionário de dados do Sistema de Estoque e Vendas do Mercado Santana. O objetivo é documentar as entidades, os atributos, os relacionamentos, as regras de acesso e as características técnicas previstas para o banco de dados do mercadinho.

O sistema tem como finalidade apoiar o controle dos produtos comercializados, das categorias, das entradas de mercadorias, das vendas e das movimentações de estoque.

2. Sistema Gerenciador de Banco de Dados

Item Definição Justificativa
SGBD MySQL 8.0 Sistema gerenciador de banco de dados relacional adequado para organizar e consultar as informações do mercadinho.
Mecanismo de armazenamento InnoDB Suporta transações, integridade referencial e chaves estrangeiras. É adequado para operações de estoque e vendas.
Codificação utf8mb4 Permite armazenar caracteres acentuados, caracteres especiais e diferentes símbolos utilizados nos dados.
Collation utf8mb4_0900_ai_ci Permite comparações que desconsideram acentos e diferenças entre letras maiúsculas e minúsculas.

Observação: as configurações acima representam a padronização técnica proposta para o projeto. Devem ser conferidas com a configuração efetivamente utilizada no banco de dados.

4. Entidades e Dicionário de Dados

Esta seção apresenta as oito entidades identificadas no modelo conceitual: CATEGORIA, PRODUTO, ENTRADA, ITEM_ENTRADA, FORNECEDOR, VENDA, ITEM_VENDA e MOVIMENTACAO_ESTOQUE.

Os tipos físicos apresentados são propostas para MySQL 8.0 e devem ser confirmados na conversão para o modelo lógico.

4.1 CATEGORIA

Classifica os produtos do mercado em grupos.

Atributo Tipo Chave Descrição
id_categoria INT PK Identificador único da categoria.
nome VARCHAR(80) - Nome da categoria.

4.2 PRODUTO

Armazena os produtos comercializados e seus dados de preço e estoque.

Atributo Tipo Chave Descrição
id_produto INT PK Identificador único do produto.
nome VARCHAR(120) - Nome ou descrição do produto.
preco_venda DECIMAL(10,2) - Preço de venda atual do produto.
quantidade_estoque INT - Quantidade atualmente disponível em estoque.
estoque_minimo INT - Quantidade mínima definida para sinalizar necessidade de reposição.
id_categoria INT FK Categoria à qual o produto pertence.

4.3 ENTRADA

Registra o recebimento de mercadorias e a nota fiscal correspondente.

Atributo Tipo Chave Descrição
id_entrada INT PK Identificador único da entrada.
data_entrada DATE - Data do recebimento das mercadorias.
numero_nota_fiscal VARCHAR(30) - Número da nota fiscal relacionada à entrada.
valor_total DECIMAL(10,2) - Valor total da entrada.
id_fornecedor INT FK Fornecedor responsável pelo fornecimento.

4.4 ITEM_ENTRADA

Entidade associativa que detalha os produtos que compõem cada entrada. Permite registrar vários produtos em uma mesma entrada.

Atributo Tipo Chave Descrição
id_item_entrada INT PK Identificador único do item da entrada.
quantidade INT - Quantidade do produto recebida na entrada.
custo_unitario DECIMAL(10,2) - Custo de uma unidade do produto na entrada.
subtotal DECIMAL(10,2) - Subtotal do item, calculado pela quantidade multiplicada pelo custo unitário.
id_produto INT FK Produto recebido.
id_entrada INT FK Entrada à qual o item pertence.

4.5 FORNECEDOR

Armazena os dados de identificação e contato dos fornecedores do mercado.

Atributo Tipo Chave Descrição
id_fornecedor INT PK Identificador único do fornecedor.
nome VARCHAR(120) - Nome ou razão social do fornecedor.
telefone VARCHAR(20) - Telefone de contato do fornecedor.
endereco VARCHAR(200) - Endereço do fornecedor.

4.6 VENDA

Registra os dados gerais de cada operação de venda realizada no mercado.

Atributo Tipo Chave Descrição
id_venda INT PK Identificador único da venda.
data_hora DATETIME - Data e horário em que a venda foi realizada.
valor_total DECIMAL(10,2) - Valor total da venda.
forma_pagamento VARCHAR(30) - Forma de pagamento utilizada.

Como funciona a leitura da entidade VENDA?

A leitura de VENDA começa pela identificação do registro por id_venda. Em seguida, podem ser consultados data_hora, valor_total e forma_pagamento.

Para saber quais produtos foram vendidos e em quais quantidades, deve-se consultar ITEM_VENDA usando id_venda. Cada item informa o produto por id_produto, a quantidade, o preço unitário e o subtotal. Assim, VENDA guarda o resumo da operação e ITEM_VENDA guarda seu detalhamento.

4.7 ITEM_VENDA

Entidade associativa que detalha os produtos incluídos em cada venda, resolvendo o relacionamento muitos-para-muitos entre VENDA e PRODUTO.

Atributo Tipo Chave Descrição
id_item_venda INT PK Identificador único do item vendido.
quantidade INT - Quantidade do produto incluída na venda.
preco_unitario DECIMAL(10,2) - Preço unitário aplicado no momento da venda.
subtotal DECIMAL(10,2) - Subtotal do item, calculado pela quantidade multiplicada pelo preço unitário.
id_venda INT FK Venda à qual o item pertence.
id_produto INT FK Produto vendido.

4.8 MOVIMENTACAO_ESTOQUE

Registra alterações nas quantidades em estoque e pode estar relacionada a um produto, a um item de entrada ou a um item de venda, conforme o evento que originou a movimentação.

Atributo Tipo Chave Descrição
id_movimentacao_estoque INT PK Identificador único da movimentação.
tipo VARCHAR(20) - Classificação da movimentação, por exemplo entrada ou saída.
quantidade INT - Quantidade movimentada.
data_hora DATETIME - Data e horário em que ocorreu a movimentação.
motivo VARCHAR(120) - Justificativa ou origem da movimentação.
id_produto INT FK Produto cujo estoque foi movimentado.
id_item_entrada INT FK opcional Item de entrada que originou a movimentação, quando aplicável.
id_item_venda INT FK opcional Item de venda que originou a movimentação, quando aplicável.

Observação: a regra de obrigatoriedade de id_item_entrada e id_item_venda, bem como a restrição para impedir referências simultâneas incompatíveis, deve ser definida no modelo lógico e nas regras de negócio.

5. Relacionamentos entre as Entidades

Entidades Cardinalidade Descrição
CATEGORIA — PRODUTO 1:N Uma categoria pode possuir vários produtos; cada produto está associado a uma categoria.
PRODUTO — ITEM_ENTRADA 1:N Um produto pode aparecer em vários itens de entrada.
ENTRADA — ITEM_ENTRADA 1:N Uma entrada contém um ou vários itens; cada item pertence a uma entrada.
FORNECEDOR — ENTRADA 1:N Um fornecedor pode fornecer várias entradas; cada entrada está vinculada a um fornecedor.
VENDA — ITEM_VENDA 1:N Uma venda possui um ou vários itens; cada item pertence a uma venda.
PRODUTO — ITEM_VENDA 1:N Um produto pode aparecer em vários itens de venda.
PRODUTO — MOVIMENTACAO_ESTOQUE 1:N Um produto pode gerar várias movimentações de estoque.
ITEM_ENTRADA — MOVIMENTACAO_ESTOQUE Opcional Uma movimentação pode referenciar um item de entrada como origem.
ITEM_VENDA — MOVIMENTACAO_ESTOQUE Opcional Uma movimentação pode referenciar um item de venda como origem.

Os relacionamentos muitos-para-muitos entre ENTRADA e PRODUTO e entre VENDA e PRODUTO são resolvidos pelas entidades associativas ITEM_ENTRADA e ITEM_VENDA, respectivamente.

7. Regras de Negócio

  1. Cada produto deve estar associado a uma categoria.
  2. Uma categoria pode possuir vários produtos.
  3. Cada entrada deve estar vinculada a um fornecedor.
  4. Uma entrada pode conter vários produtos por meio de ITEM_ENTRADA.
  5. Uma venda pode conter vários produtos por meio de ITEM_VENDA.
  6. As movimentações devem registrar produto, quantidade, tipo, data e motivo.
  7. As entradas de mercadorias devem aumentar o estoque dos produtos correspondentes.
  8. As vendas devem diminuir o estoque dos produtos vendidos.
  9. O sistema deve evitar que as operações resultem em estoque negativo.
  10. As alterações no estoque devem respeitar as regras definidas pelo responsável pelo mercado.

9. Segurança, Auditoria e LGPD

9.1 Dados tratados

Dados Finalidade Observação
Nome e preço dos produtos Cadastro e comercialização de produtos. Em regra, são dados operacionais e não pessoais.
Identificação da categoria Organização dos produtos. Não representa, por si só, dado pessoal.
Data, número da nota fiscal e valor da entrada Registro e conferência de entradas de mercadorias. Documentos fiscais completos podem conter dados pessoais.
Data, horário, valor e forma de pagamento da venda Registro e consulta das vendas. Os atributos listados não incluem cadastro específico de clientes.

Registros de auditoria, caso implementados Verificação de acessos e operações. Podem conter dados pessoais se identificarem usuários.

9.2 Bases legais

A aplicação da Lei Geral de Proteção de Dados Pessoais (LGPD - Lei nº 13.709/2018) depende dos dados efetivamente tratados e da finalidade de cada operação.

  • Cumprimento de obrigação legal ou regulatória: pode ser aplicável à manutenção de documentos fiscais e contábeis exigidos por lei.
  • Execução de contrato: pode ser aplicável quando o tratamento for necessário para executar uma relação contratual.
  • Exercício regular de direitos: pode ser aplicável quando os dados forem necessários para o exercício de direitos em processos judiciais, administrativos ou arbitrais.
  • Legítimo interesse: pode ser considerado em situações específicas, após avaliação de finalidade, necessidade e direitos do titular.

Essas são possibilidades, não uma definição automática da base legal para todos os registros. O responsável pelo tratamento deverá confirmar a base adequada para cada finalidade.

9.3 Retenção e descarte

Os dados devem ser mantidos pelo período necessário às finalidades operacionais e ao cumprimento das obrigações legais aplicáveis. Documentos fiscais e contábeis devem respeitar os prazos específicos exigidos para cada tipo de documento.

O prazo exato de retenção não está definido no modelo fornecido. Os registros fiscais e contábeis deverão ser mantidos durante os prazos exigidos pela legislação aplicável. Os registros operacionais e de auditoria deverão ter prazo formal definido pelo responsável pelo mercado. Ao fim da finalidade e dos prazos legais aplicáveis, os dados pessoais deverão ser eliminados ou anonimizados, ressalvadas as hipóteses legais de conservação.

9.4 Medidas de segurança e auditoria

  • Limitar o acesso ao banco de dados às pessoas autorizadas.
  • Utilizar senhas fortes e proteger as credenciais de acesso.
  • Evitar o compartilhamento de contas de usuário.
  • Registrar operações relevantes de acesso e alteração, caso o mecanismo de auditoria seja implementado.
  • Definir quem poderá consultar e administrar os registros de auditoria.
  • Não registrar senhas ou credenciais em logs.
  • Estabelecer prazo de retenção para os registros de auditoria.
  • Manter cópias de segurança e testar a recuperação dos dados.
